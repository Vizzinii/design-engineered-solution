## 一、详细自检问题（按文档结构分组）

### 总纲与背景

- 是否在开头用一两句话定义了“这是什么工程、目标是什么”？
- 是否说明了为什么必须用工程化方法组织（问题复杂度、约束、风险），而不是直接罗列产品？
- 目标是否可理解为可验收的方向，而不是一句口号？

### 总体设计

- 是否先写了“谁负责、怎么管控、统一什么标准”，再排步骤？
- 责任是否落到具体角色，并说明谁验收？
- 各环节之间是否有统一的交接与评审方式？

### 系统分解

- 是否按时间（阶段）、环境（域/范围）、对象（优先级）分解？
- 每个阶段是否有明确的输入、输出和验收条件？
- 是否说明了试点、分批、先后次序的选择原则？

### 验收与验证

- 每阶段“怎么算完成”是否可判定（数值或约定指标）？
- 验收是否与前面的需求一一对应（可追溯）？
- 判定由谁负责（客户、原厂、第三方）是否明确？
- 验证手段是否真实存在（测试、压测、演练、数据校验），而不是“确保”二字带过？

### 风险与偏差

- 每个阶段是否写明主要风险、应对措施和责任人？
- 是否说明回退或纠偏的触发条件与时限？
- 风险是否贯穿全程，而不是只出现在上线环节？

### 协同与接口

- 各参与方（原厂、集成商、客户运维等）的责权是否清晰？
- 变更是否走统一审批，版本与脚本是否有冻结机制？
- 系统、数据、组织三类接口（连接、迁移链路、交付流转）是否交代？

### 收束与闭环

- 是否写清交付物和移交验收方式？
- 上线后是否有持续监控、优化、再验证的闭环？
- 结尾是否落回总体目标和价值承诺？

## 二、“浅显 → 深度”示例对照

| 浅显写法 | 深度写法（同样不带术语） |
|---|---|
| 确保平滑迁移、安全可控 | 割接前完成切换演练与数据一致性校验，演练通过后方可正式切换 |
| 压测指标达标 | 压测并发与响应时间对照现网基线，达标条件与判定方在验收标准中明确 |
| 建立风险应对机制 | 每个阶段说明可能影响进度与质量的主要风险、应对措施及责任人 |
| 降低改造工作量和改造成本 | 按对象全量统计与单位改造工时测算工作量，输出适配报告与风险清单 |
| 保障系统长期稳定运行 | 监控覆盖连接数、会话、锁、SQL等核心指标，配套巡检、慢SQL治理与故障预案演练 |
| 明确各方责权 | 说明谁执行、谁负责、谁验收，验收记录全程留痕可查 |

## 三、承诺分级规则

- **机制承诺**（必写必做）：建立流程、交付文档、完成演练。例如“上线前完成切换演练与回退演练”。写了就必须有对应记录。
- **数值承诺**（谨慎写）：RTO/RPO、成功率、性能倍数、校验一致率。统一写成“以项目约定目标为准，经实测与双方确认后作为验收依据”，不写无法兑现的硬数字。
- 不确定能否兑现的内容，写“建立××机制，并在项目启动后×周内交付××文档”，而不是写一个无法验收的结果。

## 四、评审输出格式建议

- 先给总体判断（定位：处于哪一层——非工程化 / 有工程框架但机制不闭环 / 机制闭环）。
- 再按严重程度给问题清单：结构缺陷 → 机制缺失 → 表述问题，每条定位到具体段落并引用原文。
- 用户要求修改时，给出“原文 → 改后”对照，并说明改动依据和参考材料。
- 最后给落地顺序（P0 必改 / P1 篇幅允许再加 / P2 锦上添花），避免一次性堆满。
